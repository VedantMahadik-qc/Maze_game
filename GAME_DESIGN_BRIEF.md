# [Working title] — Quantum Chase Horror
Design brief for Claude Code handoff. Moth Hack 2026 entry (Intermediate — "Quantum game" tier). Standalone new project — not a fork of `quantum-3d-clerk`.

## Concept
First-person horror chase. Something is hunting the player through a house. Ducking into a room breaks line of sight; the space *between* rooms is a maze that isn't fixed — it reshapes, generated by Moth's Labyrinth engine rather than a classical procedural algorithm. Goal: reach the exit and escape the house.

## The throughline
One underlying value — **proximity** (how close the thing chasing you currently is) — drives three separate systems, each using a different Atlas engine for a reason tied to what that engine actually does, not as an interchangeable horror-flavor slot:

| System | Engine (confirmed real ID) | What proximity controls | Why this engine specifically |
|---|---|---|---|
| Maze structure | **`labyrinth-v1`** | Which candidate room-connections in a graph you design actually stay "live" | You submit a level graph (`grid_size`, `num_qubits`, a `coupling_map` of possible connections); the engine quantum-samples ZZ correlations across it. **Confirmed from a real completed run**: the field that matters is `result.output.target.edge_signs` — per edge, `sign: +1` means corridor/door (open), `sign: -1` means wall (blocked). Higher proximity → `fraction` (correlation strength) closer to 1, producing a more drastically reshuffled open/blocked pattern. `mode: "emu"` for fast local dev, `mode: "qpu"` for real IBM hardware on the actual demo. |
| Audio | **`retrocausal-echo-v1`** | Which proximity-tier tap character plays | Multi-tap delay whose tap map (`depth`, `decay`) is QPU-measured — "retrocausal" cues genuinely arrive ahead of the thing that causes them, a real early-warning mechanic. Measure one `ir` (impulse response) per proximity tier once, then re-render any sound effect through that tier's `ir` cheaply without re-paying the quantum cost. The `taps` JSON output (exact time/level/pan per tap) can drive audio scheduling directly, without even downloading rendered audio. |
| Wall visuals | **`telablur-v1`** | Interpolation position between a "safe" wall image and a "wrong" wall image | Morphs `image1` toward `image2` via qubit rotation, gated by an optional `mask` so only the wall surfaces morph — furniture and doorways stay clean. Same underlying mechanism as the black hole's spin-state morph, applied to dread instead of gravity. |

## Architecture: precompute vs. live
This split falls directly out of what's continuous vs. event-triggered — it is not arbitrary, and it's the same lesson the black hole project already paid for:

- **Telablur and Retrocausal Echo are continuous functions of proximity.** Calling Atlas live, per-frame, during an actual chase is not viable — we already proved real network latency exists (this is exactly why the black hole "flyby" had to become a precomputed sequence rather than a live camera loop). Both get rendered ahead of time as a discretized sweep across the proximity range (e.g. 8–12 steps), cached locally, and blended/switched at runtime with no network call in the hot path.
- **Labyrinth is event-triggered, not continuous** — it only needs to fire at room-entry, which is already a natural transition beat (door closing, a cut) that can comfortably absorb one real API call's latency. This is the one engine safe to call live.

## Suggested stack
Reuse the pattern proven in `quantum-3d-clerk`, not its game code — the infrastructure is generically useful independent of which game calls it:
- Frontend: Three.js + Vite, same as before.
- Backend: FastAPI + `httpx`, and specifically **port over `moth_client.py`'s design** — the async worker thread so Moth calls never block a request handler, the disk cache, and critically the safe-fallback behavior (any failure returns something inert rather than raising). That defensive pattern is exactly what a chase game needs if an Atlas call is slow or fails mid-play: fail toward "the maze/wall/sound just doesn't change this time," never toward a crash.

## Atlas integration — confirmed vs. still guessed
Being direct about this because guessing here and finding out late is exactly what cost real time on the black hole side:

- **blur-v1**: real base URL, auth, and the full async asset lifecycle (register → presigned upload → complete → submit job → poll → result) are confirmed working end-to-end — this is the one engine we have actually exercised successfully.
- **tessa-image-v1**: engine ID confirmed to exist; the "phase gate, `distortion` 0.0–3.14" specifics were never independently verified against a real call in this conversation — treat as unconfirmed until tested.
- **`labyrinth-v1`**: confirmed working end-to-end with real output. Submitting with no `level_data` at all doesn't error — it falls back to a built-in default (a 3-qubit, 1×3 linear level), which is itself useful to know. Real output convention: `result.output.target.edge_signs`, `sign: +1` = corridor/door, `sign: -1` = wall.
- **`retrocausal-echo-v1`**: confirmed working end-to-end. A minimal call (just an `audio` file, no params) returns three real outputs — `result` (processed WAV), `ir` (measured impulse response, reusable to skip re-measuring), `taps` (JSON tap map). Output links are presigned S3 URLs expiring in 15 minutes — download promptly, don't cache the URL itself.
- **`telablur-v1`**: field names (`image1`/`image2`) are proven correct — the test job was accepted *and actually executed*, not rejected for shape, which is stronger evidence than a bare `202`. It failed downstream instead: `no_mask_region` — no `mask` was supplied, so the engine fell back to `image1`'s alpha channel per its documented behavior, and the test image's alpha was almost certainly fully transparent (a 69-byte placeholder), producing an all-zero mask the engine correctly refused to process. Not a contract problem — a test-fixture problem. This confirms the plan above: **always supply an explicit `mask`** rather than relying on the alpha fallback, since a real captured room image may not carry meaningful alpha data either.

**Still needed before step 1 fully closes**: one real Telablur success — resubmit with either a genuinely opaque test image or (better, since it matches the real architecture) an explicit small mask file. Labyrinth and Retrocausal Echo already have that; Telablur is the one engine without a completed success in hand yet.

## Suggested build order
1. **Verify the two unconfirmed engines first**, in isolation, reusing the `AtlasClient` class from `decay.py` (same lifecycle, new engine ID/params). Small script, a few real calls, confirm engine IDs, param names, and Telablur's two-image shape. This is the highest-uncertainty item — resolve it before anything else depends on it.
2. **Prototype the core loop with classical placeholders.** A basic room → corridor → room chase, mock/classical maze generation standing in for Labyrinth, no real Atlas calls yet. The goal here is answering "is this actually fun to play" as cheaply as possible before any quantum integration work is sunk into it.
3. **Wire in real Labyrinth calls** at the room-entry trigger once step 2's loop feels right.
4. **Build the precompute sweeps** for Telablur and Retrocausal Echo, using the confirmed contracts from step 1.
5. **Integrate**: single proximity value driving Labyrinth (live), and the precomputed Telablur/Retrocausal Echo assets (blended/switched locally).
6. Polish / demo pass.

## Open questions
- Working title: still open.
- House layout: **settled — fixed**, not variable run to run.
- What the demon actually is — **settled by design discussion, then revised by actual playtest.** First answer was a fully invisible emergent-decoherence effect (screen static/flicker/audio only, no physical presence) specifically to avoid building a character. Playing it showed that doesn't read as a threat — it feels like ambient atmosphere, not something chasing you. Revised: give it an actual position and a simple, unmodeled shape (a stretched box/capsule, not a rigged character), using the "TV-static emissive flicker" material already proven in `quantum-3d-clerk`'s `customer.js`. This keeps the original idea intact — it's still the decoherence made visible, not a separately-designed monster — while fixing two things at once: it's now actually visible, and having a real position gives the chase a direction to run from, which a corridor/room timer alone never had.
- Win/lose state: **settled — just "reach the exit" / "caught,"** nothing further.
